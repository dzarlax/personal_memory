Implementation Plan: Context Correctness Remediation

Implementation record — approved and completed on 2026-09-05

Task summary

Remediate the confirmed correctness defects F01–F14 in the unified review. The detailed executable plan is docs/superpowers/plans/2026-09-05-context-correctness-remediation.md.

Current behavior

Fact updates can leave a post-success stale cache entry; deterministic IDs can overwrite an existing fact; document search can see an old complete and new partial generation. Expiry and import outcomes are not represented consistently, and index failures can be hidden behind a successful run.

Desired behavior

Context responses distinguish complete, incomplete, duplicate, exact-collision, partial, and ambiguous outcomes. A reader cannot receive a mixed document generation as a normal result. All expiry checks use one UTC calendar-date rule.

Scope and files

Source changes cover internal/memory, internal/rag, internal/qdrant, internal/eval, cmd/indexer, their tests, and the lifecycle contract. The original implementation scope excluded deployment, production data access, and migration; commit/push/PR were later separately authorized.

Approved design decisions

  • Exact deterministic-ID collisions never overwrite; reactivation uses an explicit lifecycle transition.
  • Any dispatched mutation invalidates cache even if its response is ambiguous.
  • Saturated retrieval and failed reindexing return explicit incomplete/partial state.
  • Approved: strict RAG publication. A generation is visible only after a per-generation seal on chunk 0 and reader-side full-generation validation. Existing unsealed chunks are omitted from ordinary results as legacy_unverified until a separately approved reindex; no implicit grandfathering.

Test plan

Use controlled HTTP interleavings for cache and applied-but-error paths; unit tests for expiry, import outcomes, Qdrant envelopes and hidden summaries; race tests for memory/RAG; then go test for memory, RAG, Qdrant, eval, retrieval and integrationbundle plus make eval-public. Integration uses only an inspected isolated environment.

Risks and rollback

Result-shape changes and stricter collisions may affect old clients; publication logic may increase Qdrant reads. Ship compatibility readers before writers, keep legacy points readable, and rollback writers before deleting any data. A production migration is a separate approval.

Open questions

  • Which Task 4 publication invariant can be proven under Qdrant query semantics?
  • Should incomplete reads be a structured successful response, a typed tool error, or both with an explicit status?
  • What compatibility window is required for existing text-only MCP clients?
